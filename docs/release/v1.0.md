**The `src/` tree is the identity that matters, not the commit SHA.** The
evidence round that produced this page changed nothing under `src/`: the tree
object above is byte-identical to the one at `c0ec657`, the commit this branch
left `core-guards` at, which `git diff c0ec657 HEAD -- src/` confirms is empty.
So the code measured here is the code that was already there, and the three
commits on top of it are a split, a Dockerfile and this page.

Resolve the tag's own commit with:

```bash
git rev-list -n 1 v1.0-benchmark
git rev-parse v1.0-benchmark^{}:src   # must print ff8e101a…
```

**The case-set digest is `sha256` over `"<filename> <sha256(bytes)>"` for every
case file, newline-joined, in filename order.** It is computed identically by
`benchmarks/hard/split_hard.py:case_set_digest` and
`benchmarks/hard/score_hard.py:case_set_digest`, and `score_hard.py` writes it
into every summary it produces. A future run against cases that gained, lost or
edited even one file prints a different digest, so it is **visibly** a different
run rather than a silently different number. That property is the reason this
page can say the figures below belong to these 2000 cases and not to some later
draw.

Scored over the four battery models' verdicts, not the whole report, because
`run_self_heating_discharge` accepts no applicability declaration for the
thermal body it marches and no battery case can therefore reach `SUPPORTED` as
a whole report. Whole-report scoring gives catch rate 100 % / false reject
100 %, which measures one gap 400 times. `NEEDS.md` C.1 carries the gap;
`benchmarks/hard/README.md` carries the argument.

### How to read these numbers

They are **development-set** numbers, which means they are numbers this
benchmark's generator has been corrected against four times. That is stated at
length in `benchmarks/hard/README.md` and is the reason the hold-out exists.
Nothing on this page is the independent figure; the independent figure does not
exist yet, and will exist exactly once.

**There is deliberately no full-set figure on this page.** Printing one beside
the development figure would state the hold-out's score as a subtraction, which
defeats the seal; until the hold-out is opened, development-set metrics are the
only ones published. The battery set is not affected — it has no hold-out, so
its 400/400 is a full-set figure with nothing to protect.

## The exact commands

```bash
# Electro-thermal, development split — produced benchmarks/hard/results_hard.json
python benchmarks/hard/score_hard.py --src src \
  --cases benchmarks/hard/cases_hard --workers 4 --split dev

# Battery — produced benchmarks/hard/results_battery.json
python benchmarks/hard/score_hard.py --src src \
  --cases benchmarks/hard/cases_battery --workers 4 \
  --results benchmarks/hard/results_battery.json

# FAST test tier
python -m pytest -m "not expensive" -q -n 4

# The split, and the proof its composition is preserved
python benchmarks/hard/split_hard.py --cases benchmarks/hard/cases_hard --verify
```

`--workers 4` and `-n 4` are fixed, not `auto`: each worker carries its own
engcore import at ~200 MB, and `auto` on a many-core host exhausts RAM and dies
as a `BrokenProcessPool` with no failing case to point at.

Opening the hold-out — **once**, and not yet — is:

```bash
python benchmarks/hard/score_hard.py --src src \
  --cases benchmarks/hard/cases_hard --workers 4 \
  --split holdout --open-holdout --note "final evaluation"
```

this table is a **record**, not a lockfile, and a future run may resolve
differently.

versions and an independently resolved numpy, all four metrics, the case-set
digest and the ten false-accept ids came out identical. See
[docs/reproduce.md](../reproduce.md).

## Known, and not fixed here

1. **`mcp` and `anyio` are imported but declared nowhere.** On a machine that
   installs only what `pyproject.toml` declares, the FAST tier is **2091 passed,
   1 skipped, 1 error** against the host's **2146 passed**: 55 tests do not run.
   `tests/mcp/test_server.py` guards its import and skips cleanly while naming
   an optional `[mcp]` dependency group that does not exist;
   `tests/mcp/test_battery_boundary.py:19` does not guard, and errors at
   collection. **CI has been red for this reason on every run since
   2026-09-06 16:47**, in both the `fast` and `scientific` jobs — measured from
   `gh run list`, not inferred. `NEEDS.md` evidence round B.1, and
   `docs/reproduce.md` for the transcript. **Nothing here was changed to make
   the number look better.**
2. **The Docker image has not been built.** Docker is not installed in the
   environment this release was cut in. The `Dockerfile` is delivered unbuilt
   and unverified as an image; the clean-environment evidence above is WSL2, not
   a container.
3. **`S00709` is still a mislabelled case**, and the generator change that would
   fix it would move the ratings cases across the whole draw. Left standing on
   purpose.
4. **`results_hard.json` scores 1400 of the 2000 cases on disk**, by design. Its
   summary says so in the `scored` and `split` fields, and it carries the digest
   of all 2000 so the file is still attributable to the full set.

## What this release closed

Before it, three sources disagreed about the same number. `benchmarks/hard/
results_hard.json` — the only results file a reader could open — held
**1236/2000 (61.8 %)** from a case set that no longer exists, with a composition
(453 sound / 1547 unsound) that has not matched `cases_hard/` for two rounds.
The real numbers lived in a `results_hard.json` at the repository root, which
`.gitignore` was swallowing, because that was where `score_hard.py`'s default
`--results` resolved when run from the repository root as its own README
instructed. The README's baseline tables held a third set of figures, correct
but unattached to any file.

Fixed by making the scorer's `--results` default resolve against the script's
own directory — the tracked path — so the file a reader opens is the file the
scorer writes. One number, one place, and the digest next to it says which cases
it belongs to.
